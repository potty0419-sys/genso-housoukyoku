# 掲示板の本番運用計画

この資料は設計メモです。Supabaseへの接続・SQLの適用は行っていません。POCの投稿・通報はブラウザ内だけに保存されます。

## ストレージの切り替え

`src/js/store/Store.js` は `list / create / update / remove / report / interest` を非同期メソッドとして定義しています。実装は `LocalStore` です。`SupabaseStore.js` はコメントだけの雛形であり、読み込みません。本番では同じインターフェースからEdge Functionまたは制限したPostgres関数を呼び出します。SDK、service_roleキー、YouTube APIキー等をブラウザに置きません。

## テーブル

具体的なDDLは `supabase_schema.sql` を参照してください。

| テーブル | 主な列・用途 |
| --- | --- |
| posts | id、type（party/shout）、purpose、jobs（配列）、level_min/max、starts_at、duration_minutes、current_count/capacity、place、character_name、comment、created_at、expires_at、closed、report_count、interest_count、moderation_status、sample、delete_key_hash、actor_id、fingerprint、deleted_at |
| reports | id、post_id、reporter_id、reason、created_at。post_id＋reporter_idを一意にする |
| interests | post_id、actor_id、created_at。1人1回の参加希望用 |
| post_attempts | actor_id、fingerprint、created_at。削除後も投稿間隔・重複を判定するための短期履歴 |

時刻はtimestamptzのUTC保存、表示は日本時間。`expires_at` はpartyなら開始＋所要時間（未指定60分）、shoutなら作成＋24時間をサーバーで計算します。終了は時刻比較で判定し、定期ジョブなしでも公開APIの一覧から除外します。「終了も表示」時も通報非表示・運営非公開の投稿は返しません。ひとことの期限切れは常に返しません。

## RLSと秘密情報

- 全テーブルでRLSを有効にします。公開読取は、削除されておらず、運営公開状態で、通報数3未満のpostsに限定します。期限とフィルターは公開一覧APIでも必ず適用します。
- 公開するpostsの列だけにSELECT権限を付け、削除キーハッシュ・投稿者識別子・fingerprintを公開しません。RLSだけでは列の秘匿にならないため、`select('*')` は使用しません。
- anon/authenticatedからのINSERT/UPDATE/DELETEを許可しません。reports、interests、post_attemptsは直接の読み書きを許可しません。Edge Functionのservice_role、または最小権限の関数だけが更新します。
- 削除キーはサーバーで十分なランダム性を持たせて発行し、作成応答で一度だけ渡します。DBにはソルト付きのハッシュ（例：Argon2id）を保存します。更新・締切・削除時に照合し、公開APIはハッシュを返しません。キーをURLに載せず、ログにも残しません。
- クライアントはキーをブラウザに保存します。紛失時は原則復元不可。投稿者の操作でも文字数・人数・締切状態等をサーバーで再検証します。
- 関数を採用する場合、SECURITY DEFINERには固定search_path、明示的な実行権限、最小権限所有者を設定し、既定のPUBLIC実行権限を取り消します。

## 投稿制限と入力検証

Edge Functionを基本案とし、匿名認証ID（Supabase anonymous sign-in）と短期のHMAC化IP等を組み合わせます。画面上のログイン・DMは作りません。匿名認証IDはブラウザを消すと変わるため、同一人物判定の保証には使えません。攻撃が増えた時点で追加のチャレンジ・利用制限を段階的に導入します。

1. サーバー時刻を使い、投稿者ごとのロックを取得します。Postgres関数案では `pg_advisory_xact_lock` 等、Edge Function案でもDBトランザクション内の関数で競合を防ぎます。
2. postsの種類をまたいで、直近の成功投稿から180秒以内を拒否します。拒否応答に再試行までの秒数を含めます。
3. NFKC正規化、空白統一、職業の順序統一を行い、投稿内容のfingerprintを照合します。同内容は24時間拒否。削除後もpost_attemptsに履歴を保持します。
4. 目的・職業はサーバー側の許可リスト、レベル範囲1〜999、所要時間1〜1440分、人数1〜100と現在人数≦定員を検証します。POCの数値範囲はUI用の仮制限で、ゲームの仕様を表しません。
5. コメント140字・ひとこと40字、集合場所60字・キャラ名30字を検証します。自由記入欄全体にNG語句、URL、電話番号、メール形式の検査を適用します。Unicode・ゼロ幅文字・表記ゆれも考慮します。正規表現だけによる完全な防御はできないため、運営の目視確認も併用します。
6. サーバーでexpires_at、hash、件数等を設定し、投稿と制限履歴を同じトランザクションで保存します。クライアントから渡された通報数・作成日時・削除キーハッシュは信用しません。

LocalStoreのレート制限・通報重複排除はブラウザ内での再現です。localStorageの改変やリセットで回避できるため、本番の制限には転用しません。`window.__gensoDebug` は本番バンドルで削除してください。

## 通報・参加希望・モデレーション

- 通報APIは匿名認証IDをサーバーで確定します。reportsの一意制約により同じブラウザの通報は1件まで。報告理由を任意のカテゴリで受け付け、自由文を扱う場合は個人情報の検証を加えます。
- reportsの作成とposts.report_countの増加は、行ロック付きトランザクションで行います。重複通報では件数を増やしません。3件以上になったら公開一覧から即座に除外します。
- 非表示は違反確定ではありません。運営用の認証画面から内容・通報理由・不正な集中通報を確認し、維持・削除・復帰を決め、操作記録を残します。復帰は件数の数値だけを直接書き換えるのでなく、通報の解決記録と再判定を整合させます。
- 参加希望もinterestsの一意制約とトランザクションで増加させます。終了・満員・非表示への参加希望は拒否します。参加枠の予約や承認機能ではありません。
- 募集締切・人数更新・削除は削除キー照合後に行います。削除はまず論理削除し、短い保留期間後に物理削除します。
- 保持期間の例：ひとことは失効後7日、募集は終了後30日、通報・運営記録は90日、重複判定履歴は24時間。実際の保持期間は運用開始前に決めて告知します。バックアップ・アクセス監査・緊急停止・問い合わせ窓口を用意します。

## 利用規約・案内に書くこと

- 非公式ファンサイトであること、ゲーム運営・配信者の公式発表との区別。
- 投稿できる内容、禁止行為（個人情報、外部誘導、詐欺、嫌がらせ、なりすまし、RMT等）。ゲーム側規約も守ること。
- 集合条件や参加可否はゲーム内で当事者が確認すること。金銭のやり取りやDMを提供しないこと。
- 参加希望は数の目安であり、参加・報酬を保証しないこと。
- 投稿者の削除キー保管責任と紛失時の扱い。ブラウザの保存データ消去の影響。
- 期限切れ、通報3件での一時非表示、運営の削除・利用制限、異議申立て・問い合わせの方法。
- 匿名識別子、IP等の処理目的・保持期間・外部委託先をプライバシー案内で説明すること。
- 本番でユーザー投稿に「サンプル」を付けない運用へ移る場合の明確な表示切り替え。
